# План тестов и баланса боссов

Дата: 2026-09-10. Относится ко всей роспиcи из `Docs/Design/2026-09-10-boss-concepts-roster.md` и ко всем планам реализации из `Docs/superpowers/plans/2026-09-10-boss-roster-roadmap.md`.

Этот документ не про то, «как тестировать вообще», а про **одну конкретную опасность**: в автобое игрок не может компенсировать плохо настроенного босса мастерством. Если числа неверны, бой не «сложный» — он непроходимый, причём избирательно для одного персонажа. Всё ниже построено вокруг того, чтобы поймать это до плейтеста, а не после.

## 2. Пять уровней проверки

Каждый уровень ловит свой класс ошибок. Пропуск уровня означает, что его ошибки найдёт игрок.

### Уровень 1 — чистая логика (EditMode, без сцены)

Что покрывает: `BossEncounterState` (фазы, кулдауны, телеграфы, циклический порядок), `BossPoolSelector`, будущие чистые правила.
Образец: `Assets/Tests/EditMode/BossEncounterTests.cs`, секция «BossEncounterState (чистая логика)».
Правило: **любая новая механика получает тест этого уровня до кода.** Он дешёвый и детерминированный.

### Уровень 2 — интеграция через живой `CombatManager.Tick`

Что покрывает: что способность действительно что-то делает с игроком/боссом — урон прошёл, щит выдан, навык заблокирован, спрайт сменился.
Образец: `TickBossEncounters_HeavyAttackAbility_ExecutesAfterTelegraphAndDamagesPlayer`.
Правило: **на каждый новый `BossAbilityEffectKind` — минимум три теста:** эффект применяется; эффект уважает свой потолок/кламп из правил честности; эффект не падает в вырожденном случае (нет оружия, нет навыков, цель мертва).

### Уровень 3 — целостность контента (EditMode + `AssetDatabase`)

Что покрывает: ассеты, собранные руками в YAML. Это самый вероятный источник тихих ошибок: не тот guid, не то числовое значение `effectKind`, вывернутый диапазон этажей.
Образец: `ContentSyncTests.cs`.
Правило: **правила честности из раздела 0.4 спеки проверяются тестом, а не глазами.** Конкретно:

| Правило | Проверка |
|---|---|
| Блокировка навыка ≤ 8 с | по всем китам: `disruptSeconds <= MaxBossSkillDisruptSeconds` |
| Блокировка навыка телеграфируется ≥ 3 с | по всем китам: `telegraphSeconds >= 3f` для `DisruptSkills` |
| Опасная способность телеграфируется ≥ 1.5 с | по всем китам: `HeavyAttack` с `damageMultiplier >= 1.5` имеет `telegraphSeconds >= 1.5` |
| Броня не обнуляется | по всем китам: суммарный `StatDebuff` по броне ≤ 50 % |
| Лечение режется ≤ 50 % | по всем китам: `HealCut` ≤ 50 |
| Каждый этаж покрыт пулом | `BossPoolSelector.Select` не возвращает `null` на этажах 1..`DungeonManager.TotalFloors` |
| У босса есть спрайт и кит | все `MonsterData.isBoss` в пуле имеют `sprite != null`, `bossKit != null` |

Эти тесты пишутся **один раз** и потом ловят каждый новый ассет роспиcи автоматически. Это самая выгодная работа во всём плане тестов.

### Уровень 4 — смоук всего флоу (PlayMode)

Что покрывает: что бой с новым боссом вообще запускается в реальной сцене, UI телеграфа рисуется, награда выдаётся, забег продолжается.
Команда:

```bash

```

**Перед запуском — бэкап файла сохранения:** смоук затирает прогресс.
Правило: запускается один раз на план, а не на каждый таск.

## 3. `BossBalanceRunner` — что построить

Новый editor-раннер по образцу `VeteranBalanceRunner.cs`, использующий существующий `CombatSimulationEngine`.

**Матрица прогона:** каждый босс × 3 персонажа × 3 профиля сборки × 30 сидов.

Три профиля сборки на персонажа, а не 24 — цель другая, чем у аттестации: не «оценить сборку», а «поймать непроходимость».

| Профиль | Что это | Зачем |
|---|---|---|
| **Бедный** | уровень персонажа по этажу, стартовое снаряжение, ноль улучшений зданий | нижняя граница: игрок, которому не повезло. Если он не проходит — босс слишком жёсткий |
| **Средний** | медианное снаряжение своего этажа, здания на 2 | основной ориентир |
| **Богатый** | лучшее снаряжение этажа, здания на 4, профильные навыки | верхняя граница: босс не должен умирать за 5 секунд |

**Что писать в CSV на каждый прогон:** boss id, персонаж, профиль, этаж, сид, результат (победа/поражение), виртуальное время боя, HP игрока в конце (%), число резолвов каждой способности босса, доля полученного урона по источникам (обычные атаки / тяжёлые / DoT / фоновый тик).

Последняя колонка — самая важная. Она отвечает на вопрос «почему игрок умер», без которого тюнинг превращается в угадывание.

**Выход:** `Docs/Balance/BossBalance_<дата>.csv` + сводка по (босс × персонаж).

## 4. Целевые числа

Стартовые ориентиры, а не догма — но выход за них требует объяснения в коммите.

### Проходимость

| Метрика | Цель | Красная зона |
|---|---|---|
| Win rate, средний профиль | 60–80 % | < 45 % или > 95 % |
| Win rate, бедный профиль | ≥ 35 % | < 20 % |
| Win rate, богатый профиль | ≥ 90 % | < 75 % |
| **Разброс win rate между тремя персонажами** | **≤ 20 п.п.** | **> 30 п.п.** |
| Win rate Вайолет | не ниже минимума из двух других минус 15 п.п. | ниже этого — босс переделывается, а не подкручивается |

Строка про Вайолет отдельная не для симметрии: у неё 15 HP базы против 45 у Саши, и почти каждое непроходимое сочетание в роспиcи бьёт именно по ней. Это главный автоматический предохранитель всего плана.

### Темп боя

| Метрика | Цель | Что значит выход |
|---|---|---|
| Время боя, средний профиль | 25–60 с | < 20 с — босс не успевает показать механику, фазы не наступают; > 90 с — нужен enrage |
| Число резолвов сигнатурной способности за бой | ≥ 3 | босс определяется своей способностью; если она срабатывает 1 раз, игрок её не запомнит |
| Доля боёв, дошедших до последней фазы | ≥ 70 % на среднем профиле | фазы, которых никто не видит, — выброшенная работа |

### Урон

| Правило | Проверка |
|---|---|
| Одиночный удар ≤ 50 % макс. HP цели | в CSV: максимальный зафиксированный единичный урон / MaxHP |
| Фоновый урон (`RoomTick`) считается в % от макс. HP | проверяется тестом уровня 3, а не симуляцией |
| DoT конечен | суммарный урон DoT за бой ≤ 35 % макс. HP на среднем профиле |

## 5. Процедура на каждого нового босса

Чеклист, который проходит каждый босс роспиcи перед тем, как считаться готовым.

- [ ] Тесты уровня 1 на новую чистую логику (если она есть) — написаны до кода
- [ ] Три теста уровня 2 на каждый новый `effectKind`: применяется / уважает потолок / не падает в вырожденном случае
- [ ] Ассет проходит все проверки уровня 3 (они общие, отдельных писать не надо)
- [ ] EditMode зелёный целиком, exit code 0
- [ ] `BossBalanceRunner` прогнан, CSV закоммичен в `Docs/Balance/`
- [ ] Все метрики раздела 4 в зелёной зоне; каждое отклонение объяснено в коммите
- [ ] PlayMode-смоук `RESULT=PASS` (один раз на план, не на босса)
- [ ] **Ручной плейтест: пройти босса каждым из трёх персонажей**
- [ ] Ответ на вопрос «что игрок делает в этом бою» совпадает с колонкой «Решение игрока» из спеки

Последний пункт — не формальность. Если по ощущению от плейтеста босс, заявленный как «приоритет цели», играется как «стой и смотри», значит числа сделали решение неважным, и это баг баланса, а не вкусовщина.

## 6. Что автоматика поймать не сможет

Признаём честно, чтобы не полагаться на зелёные тесты там, где они ничего не гарантируют.

- **Читаемость телеграфа.** Симуляция не знает, успевает ли игрок прочитать баннер. Только глаза.
- **Ощущение от блокировки навыка** (Тюремщик). Метрики покажут проходимость; «отобрали геймплей» они не покажут.
- **Понятность приоритета цели** (Близнецы, Свечник, Амальгам, Паучиха). Симуляция бьёт по оптимальной цели по определению — живой игрок сначала должен догадаться, что цель надо менять. Это прямо проверяется на плейтесте: если тестер не переключил цель ни разу, механика не доносится, и виноват не тестер.
- **Не превратился ли бой в разглядывание полоски.** 60 секунд по метрикам и 60 секунд по ощущению — разные вещи.

Для трёх боссов с приоритетом цели стоит завести отдельный измеряемый показатель на плейтесте: **сколько раз тестер сменил цель за бой**. Ноль означает, что механика не работает, независимо от win rate.
