# openDAW MCP — дизайн

Дата: 2026-09-08
Статус: утверждён, готов к плану реализации

## Задача

Дать Claude Code возможность писать музыку для DungeonGirls в openDAW вместо Reaper:
собрать аранжировку с нуля, отрендерить микс и стемы, отдать бесшовный луп для Unity.

## Решения, принятые до дизайна

| Вопрос | Решение |
|---|---|
| Объём цикла | Полный: генерация аранжировки с нуля плюс рендер |
| Источники звука | Синтез + сэмплы + soundfont (Vaporisateur, Neon, Nano, Playfield, Soundfont) |
| Обратная связь | Односторонний поток. Ручные правки в UI — конечная точка, обратно в MCP не возвращаются |
| Версионность проектов | Не нужна |
| Выход | WAV + бесшовный луп + стемы |
| Форма инструментов | Декларативный документ + узкий набор инструментов |
| Язык | TypeScript |
| Расположение | `Tools/opendaw-mcp/` в репозитории DungeonGirls |
| Параметры устройств | Строгая валидация по каталогу, генерируемому из адаптеров |

## Что подтверждено спайком

Спайк (одноразовый, в scratchpad) поднимал openDAW в headless-Chromium через Playwright
и рендерил проект из двух инструментов.

| Проверка | Результат |
|---|---|
| `crossOriginIsolated` в headless | `true`, `SharedArrayBuffer` доступен |
| WASM-движок | `ensureReady=true` |
| Ненулевой звук | Микс 131040 сэмплов, пик 0.687 |
| Стемы отдельными парами | 4 канала = 2 пары, пики 0.548 и 0.303 — реальное разделение |
| Рендер по диапазону | 83040 сэмплов при длине диапазона 48000 — см. поправку ниже |

> **Поправка от 2026-09-09 (по итогам реализации).** Вывод из этой строки был неверен.
> `ExportRange.end` **не обрезает** рендер: он идёт только в предохранитель `maxDurationSeconds`,
> а останов происходит по детекции тишины. Обрезает лишь `range.start` (перемотка). В спайке
> `range.end` случайно совпал с концом аранжировки, из-за чего лишние сэмплы выглядели как хвост
> затухания. Проверено по `OfflineEngineRenderer.ts:236-251,351` и
> `core-wasm/src/offline-worker.ts:303-350`. Следствия — в разделе «Луп».

Две поломки, которые повторятся в настоящем сервере и уже учтены в дизайне:

1. Движок запрашивает `${wasmUrl}/wasm/engine.wasm`. Отдавать надо корень `dist/`
   пакета `@opendaw/studio-core-wasm`, иначе прилетает `index.html` и падает
   `WebAssembly.compile(): expected magic word`.
2. Vite префбандлит часть `@opendaw/*` и оставляет часть как есть — получаются две копии
   `studio-boxes`, и `Project.new` падает на `AudioUnitBox is not instance of AudioUnitBox`.
   Лечится `optimizeDeps.exclude` плюс `resolve.dedupe` по всему списку `@opendaw/*`.

## Опорные факты об openDAW

Проверены по коду, не по документации.

- Патчить openDAW не требуется. `ProjectApi` из `@opendaw/studio-core` — штатный публичный
  API авторинга: `setBpm`, `createInstrument`, `insertEffect`, `createNoteTrack`,
  `createNoteRegion`, `createNoteEvent`, `quantiseNotes`, автоматизация, аудио-регионы.
- `OfflineEngineRenderer.start(project, Option<ExportConfiguration>, progress, signal, sampleRate)`
  возвращает `AudioData`. Работает в Worker, принимает сериализованный проект, UI не нужен.
- `ExportConfiguration = {stems?, metronome?, range?}`, где
  `ExportRange = "full" | {start: ppqn, end: ppqn}`,
  а `stems: Record<string, ExportStemConfiguration>` с ключом `UUID.toString(unit.uuid)`.
- `ExportConfiguration.stemFileNames(config)` даёт имена в порядке каналов. Собирать имена
  самостоятельно обходом `stems` нельзя: метроном добавляется последней парой внутри
  движка, самостоятельный обход даёт на одно имя меньше и пишет `undefined.wav`.
- `PPQN.Quarter = 960`, `PPQN.Bar = 3840`. Каноническая запись позиции — `такт.доля.шестнадцатая:тики`,
  1-based (`PPQN.toString`).
- `MidiKeys.toFullString(note) = Names.English[note % 12] + (floor(note / 12) - 2)`,
  то есть **60 = C3**, не C4.
- Шины существуют: `AudioUnitType = instrument | bus | aux | output`. Образец создания —
  `createAudioBusUnit` в `DawProjectImporter`.
- Параметры устройств интроспектируются: `namedParameter` у адаптера — вложенный объект
  с человеческими ключами, каждый параметр несёт `valueMapping` (диапазон), `stringMapping`
  (единица, знаки после запятой либо список меток для дискретных) и отображаемое имя.
  `ParameterAdapterSet.parameters()` перечисляет всё.
- `WavFile` умеет писать 16 бит (`encodeInts16`) и 32 бита float (`encodeFloats`).
  24 бита читает, но не пишет.
- Рендер идёт на `project.copy()`: `OfflineEngineRenderer.start` временно гасит зону лупа.

## Архитектура

Три части с разделёнными ответственностями.

**`host/`** — статическая страница на vite, собирается один раз в `host/dist/`.
Загружает openDAW по последовательности из `boot.ts` (Workers → AudioWorklets →
AudioContext → WasmEngine) и выставляет `window.__odaw` с примитивами
`build`, `render`, `bundle`, `inspect`, `describe`, `importAsset`, `listAssets`, `reset` —
по одному на каждый инструмент MCP. Единственное место, где код касается API openDAW. Зависимости — с npm по точным версиям (`studio-core@0.2.4`,
`core-wasm@0.0.15`), не из локальной сборки `C:\Tools\openDAW`.

**`src/`** — MCP-сервер на stdio. Валидирует документ, пишет WAV, отдаёт пути.
Про openDAW не знает ничего.

**`src/bridge.ts`** — Playwright плюс статическая отдача `host/dist` со своими
заголовками COOP/COEP (свой сервер на Node, vite в продакшене не нужен).

Поток данных односторонний:

```
Claude → build(документ) → страница строит Project
                              ↓
                    render(mix | stems | range)
                              ↓
              Float32Array[] → сервер → WAV на диск
                              ↓
              (опционально) bundle() → .odb для ручных правок
```

Браузер поднимается лениво на первом инструменте и живёт до конца сессии: холодный
старт стоит секунды из-за WASM. Проект живёт в памяти страницы между вызовами, поэтому
`build` и `render` — разные инструменты: можно построить один раз и отрендерить микс,
стемы и несколько диапазонов без пересборки.

Следствия, принятые сознательно:

- Перезапуск сервера теряет проект. Смягчение: `build` принимает документ целиком и
  детерминирован, повтор вызова восстанавливает состояние.
- Один проект за раз. Менеджер сессий при одностороннем потоке не оправдан.

## Формат документа

Позиции — в нотации openDAW: `такт.доля.шестнадцатая`, 1-based. Длительности — музыкальными
дробями: `1/4`, `1/8.`, `1/8t`, `2b`. Синтаксис намеренно разный, перепутать нельзя.
Высота — `"C3"` либо число (60 = C3).

Паттерны отделены от расстановки: игровая музыка повторяется, без этого документ на
четырёхминутный трек распухает до десятков килобайт одинаковых нот.

```jsonc
{
  "name": "CombatTheme_Jennifer",
  "tempo": 132,
  "signature": "4/4",
  "end": "33.1",
  "loop": {"start": "1.1", "end": "33.1"},

  "buses": [
    {"name": "Drums", "stem": "drums"},
    {"name": "Harmony", "stem": "harmony",
     "effects": [{"device": "Dattorro", "params": {"wet": 0.25}}]}
  ],

  "patterns": {
    "bass_drive": {
      "length": "2b",
      "notes": [
        {"p": "C2", "at": "1.1",   "d": "1/8"},
        {"p": "C2", "at": "1.1.3", "d": "1/8", "v": 0.6},
        {"p": "G2", "at": "1.3",   "d": "1/8"}
      ]
    }
  },

  "tracks": [
    {
      "name": "Bass",
      "instrument": {"device": "Neon", "params": {"cutoff": 0.35}},
      "effects": [{"device": "Delay"}],
      "mix": {"volume": -4, "pan": 0},
      "out": "Harmony",
      "place": [{"pattern": "bass_drive", "at": "1.1", "repeat": 8}]
    }
  ]
}
```

Позиции внутри паттерна отсчитываются от его начала. `repeat` разворачивается в отдельные
регионы, которые openDAW покажет как обычные и позволит править поштучно.

Сэмплерные инструменты ссылаются на импортированные ассеты по имени, под которым их вернул
`list_assets`. Имя, а не UUID: UUID генерируется при импорте и меняется от прогона к прогону,
из-за чего документ переставал бы быть воспроизводимым — а на воспроизводимости держится
восстановление состояния после перезапуска сервера.

```jsonc
{"name": "Drums",  "instrument": {"device": "Playfield",
                                  "slots": {"C1": "kick_deep", "D1": "snare_tight"}}}
{"name": "Pad",    "instrument": {"device": "Nano", "sample": "choir_ah"}}
{"name": "Strings","instrument": {"device": "Soundfont",
                                  "soundfont": "FluidR3_GM", "preset": 48}}
```

Ссылка на неимпортированный ассет — ошибка схемы, а не тихая тишина в миксе.

`out` направляет дорожку в шину, стем экспортируется с шины. Дорожка без `out` идёт прямо
в мастер и, если у неё есть собственный `stem`, становится отдельным стемом. Группировка —
не отдельный механизм, а следствие штатной маршрутизации.

Умолчания: `v` (velocity) = 0.8, `mix.volume` = 0 dB, `mix.pan` = 0.

Сознательно не входит в формат:

- Шаговая сетка для ударных. Читается лучше, но это вторая грамматика и второй парсер.
  Playfield адресует слоты высотой, обычного списка нот достаточно.
- Автоматизация параметров по времени. `ProjectApi` её умеет, но она не заказана и заметно
  усложняет формат. Добавляется потом отдельным полем, не ломая существующее.
- Нормализация и целевой LUFS. Для игровых стемов громкость обычно выравнивается микшером
  Unity, а не запекается в файл.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `describe_devices` | Каталог инструментов и эффектов с параметрами: имя, диапазон, единица, умолчание, метки дискретных значений. Читающий. |
| `build_arrangement` | Принимает документ, строит проект. Возвращает сводку: дорожки, шины, число регионов и нот, длину в тактах и секундах, предупреждения. |
| `inspect_project` | Что сейчас построено. |
| `render` | `target: "mix" \| "stems"`, необязательные `range`, `loop`, `format`. Пишет WAV, возвращает пути, длительность и пик по каждому файлу. |
| `import_asset` | Кладёт файл с диска в проект. По расширению: `wav`/`mp3`/`flac` → сэмпл, `sf2` → soundfont. Имя по умолчанию — имя файла без расширения, переопределяется параметром. |
| `list_assets` | Что импортировано: имена для ссылок из документа, тип, длительность, для soundfont — список пресетов. |
| `export_bundle` | `.odb` на диск для ручных правок в UI. |
| `reset_project` | Чистый лист без перезапуска браузера. |

`describe_devices` — несущая конструкция строгой валидации, а не удобство. Каталог
**генерируется**: каждое устройство поднимается один раз во временном проекте, дальше
обход `namedParameter`. Оба конца — каталог и валидатор — берут схему из адаптеров openDAW,
поэтому расхождение с их кодом невозможно по построению.

## Обработка ошибок

Три класса, обходятся по-разному.

- **Документ не прошёл схему.** Отказ целиком, до касания браузера, со списком проблем и
  путями до полей (`tracks[2].place[0].pattern: паттерн "lead_b" не объявлен`). Частично
  построенный проект хуже отсутствующего: он молча звучит не так.
- **Упало внутри страницы.** Возвращаются сообщение и стек, проект помечается негодным,
  следующий вызов требует `build_arrangement` заново.
- **Браузер умер.** Мост поднимает заново и честно сообщает, что состояние потеряно.
  Тихое воскрешение с пустым проектом запрещено: оно превращает сбой в необъяснимо
  тихий рендер.

Схемой, а не движком, ловятся: высота вне диапазона MIDI, нулевая длительность, позиция
за `end`, ссылка на необъявленный паттерн или шину, неизвестное имя параметра, значение
параметра вне диапазона.

## Рендер, стемы, луп

Рендер идёт на `project.copy()`. По умолчанию 16 бит, 48 кГц; `format: "float32"` — если
нужна дальнейшая обработка снаружи. Пик считается всегда и возвращается по каждому файлу;
при пике больше 1.0 в ответ кладётся предупреждение, потому что `encodeInts16` клиппирует
молча.

Стемы: ключ `stems` — `UUID.toString(unit.uuid)`; имена файлов берутся **только** из
`ExportConfiguration.stemFileNames(config)`.

Луп строится свёрткой хвоста на голову. Рендер отдаёт `L + T` сэмплов, где `L` —
длина лупа, `T` — хвост до затухания:

```
out[i] = render[i] + render[i + L]      для i < min(L, T)
out[i] = render[i]                       для остальных
длина out = L
```

Реверб, дилей и релизы огибающих заворачиваются точно, без кросс-фейда, который смазал бы
атаку на стыке. При `T > L` свёртка повторяется порциями по `L`. Для стемов применяется к
каждой паре каналов отдельно теми же `L` и `T`, поэтому стемы остаются фазово-сходящимися
и в сумме дают ровно микс.

Границы применимости, проверяемые при сборке и сообщаемые в ответе `render`:

- Нота, тянущаяся через точку лупа, не заворачивается: свёртка чинит затухания, а не
  незакрытые ноты.
- Рендер начинается с тишины на `loop.start`. Если что-то звучит с более раннего места,
  в лупе этого не будет.

Обе ситуации выявляются одной проверкой: пересекает ли регион `loop.start`.

**Обязательное условие, выясненное при реализации:** рендер лупа допустим только когда
`loop.end` совпадает с `end` документа. Причина в поправке выше: движок не обрезает рендер по
концу диапазона, поэтому всё, что стоит в аранжировке после `loop.end`, продолжает звучать и
попадает в то, что свёртка считает хвостом затухания. Свернув его, мы завернём на начало лупа
настоящую музыку следующих тактов — слышимую кашу. `loop.start` при этом любой: интро до точки
лупа работает штатно (перемотка на `loop.start`, игра до конца, дальше чистое затухание).
Инструмент `render` проверяет это условие и отказывает с объяснением, а не выдаёт артефакт молча.

## Раскладка

```
Tools/opendaw-mcp/
  host/
    src/main.ts          # window.__odaw
    vite.config.ts       # COOP/COEP, dedupe @opendaw/*, отдача wasm из dist/
  src/
    schema.ts            # zod-схема документа

    expand.ts            # паттерны + repeat -> регионы и ноты
    loop.ts              # свёртка хвоста

    bridge.ts            # Playwright + статика с COOP/COEP

  test/
```

Граница проведена так, что `time`, `pitch`, `expand`, `loop`, `schema` — чистые функции без
браузера. Там живёт большая часть логики и там же живут ошибки, которые слышны, но не видны:
октава мимо, доля мимо, шестнадцатая мимо.

## Тестирование

Разработка по TDD для чистых модулей. Три инварианта проверяются свойствами, а не примерами:

1. **Свёртка лупа.** Синтетический сигнал длины `L + T` → `out[i] == in[i] + in[i+L]`,
   длина ровно `L`. Без openDAW.
2. **Сумма стемов равна миксу.** Один проект рендерится дважды — миксом и стемами; сумма
   стемов должна совпасть с миксом в пределах ошибки округления.

   *Поправка от 2026-09-09.* Заявление, что этот тест проверяет маршрутизацию, порядок каналов
   и имена разом, было неверным: сложение коммутативно, поэтому обмен стемов местами (и даже
   схлопывание всего звука в один стем) сумму не меняет. Тест доказывает только сохранение
   энергии. Тождество «имя стема — его звук» проверяется вторым тестом: партии разнесены по
   разным тактам, и у каждого стема должна быть энергия в своём такте и тишина в чужом.
3. **Детерминизм сборки.** Один документ дважды → одинаковый набор регионов и нот.

Интеграционных тестов с настоящим браузером — единицы: загрузка, сборка, короткий рендер.
Они медленные из-за подъёма WASM, держать их много незачем.

## Риски

- **Привязка к версиям SDK.** `studio-core@0.2.4`, `core-wasm@0.0.15` пинятся точно.
  Обновление openDAW — отдельная работа с перепрогоном тестов, а не `npm update`. Наш код
  в их репозиторий не лезет, поэтому обновление ничего не затрёт молча, но и совместимость
  сама не появится.
- **Playwright тянет Chromium ~150 МБ** и обновляет его со своими релизами.
- **Стоковые устройства openDAW — весь доступный звук.** VST не будет никогда: это
  ограничение браузера, а не сервера. Если боевой теме понадобится конкретный VST-инструмент,
  MCP этого не починит. Риск принят осознанно при выборе «собирать сразу», но не устранён.
- **Свёртка лупа не спасёт непериодическую аранжировку.** Выявляется проверкой, исправляется
  только самой музыкой.

## Окружение

Установлено при подготовке (2026-09-08):

- Node.js 24.19.0 LTS (openDAW требует >= 23)
- Rust 1.98.1 stable + nightly 1.100.0 с `rust-src`, таргет `wasm32-unknown-unknown`
- mkcert 1.4.4
- openDAW в `C:\Tools\openDAW`, собран, дев-сервер на `https://localhost:8080`

Три обхода, без которых openDAW не собирается на Windows:

1. `C:\Users\volde\.cargo\env` создан вручную: `build-wasm.sh` делает `. "$HOME/.cargo/env"`,
   а winget-версия rustup этот файл не создаёт.
2. npm 11.17 блокирует install-скрипты; одобрены `esbuild`, `nx`, `protobufjs`, `@parcel/watcher`.
